# 個人 AI 長期記憶與知識管理系統
## Personal AI Memory & Knowledge System

**版本：v0.5 技術交接版**

**日期：2026 年 10 月 28 日**  
**專案狀態：尚未實作**  
**用途：架構評估、技術規格設計、AGENT DOC 與開發規劃**

---

# 1. 產品目標

建立一套本機優先、供個人長期使用、透過單一 AI Agent 操作的文字記憶與知識管理系統。

使用者可以透過 Codex Desktop、Claude Code 或其他 Agent，以自然語言保存、查詢、分析與重新理解個人資訊。

系統需支援：

- 個人日記、經歷與想法。
- 技術及其他領域的研究成果。
- 學習筆記。
- 人生目標、計畫與決策。
- 個人專案及歷史設計紀錄。
- 活動、待辦及狀態相關資訊。
- 跨時間、跨主題的個人記憶分析。

使用者不應被迫為每項內容先選擇固定分類。

核心理念：

**原始記憶忠實保存，AI 解讀可以演化，資料不能被特定模型或 Agent 綁定。**

---

# 2. 使用規模與資料型態

主要使用者：一人。

預期使用至少五年。

估計五年內約有：

- 1,300–6,500 筆原始紀錄。
- 2,000–25,000 份包含衍生內容的文字文件。

主要容量規劃範圍為 5,000–12,000 份文件，並以更高規模進行壓力測試。

只保存文字資料。

不管理圖片、音訊、影片、PDF 或 Word 原始附件。

對外部資料，可以保存來源網址、必要的文字摘錄或可合法保存的文字快照。

AI 研究報告必須與外部來源原文區分。

未保存的來源資訊不能承諾由未來模型恢復。

---

# 3. 使用體驗

使用者主要透過自然語言操作。

範例：

「記錄今天對未來工作的想法。」

「我之前研究過哪些關西腔內容？」

「比較我過去三年對工程師工作的看法。」

「重新檢查之前的研究是否有錯誤。」

「我有哪些反覆提過、卻尚未找到完成紀錄的構想？」

一般 AI 問答不應自動讀取個人記憶庫。

一般對話不得自動永久保存。

長期希望提供保守智慧查詢觸發；初期可先採明確觸發，避免誤用。

使用者能指定：

- 只查個人記憶庫。
- 不使用記憶庫。
- 先查記憶庫，再查外部資料。

---

# 4. 通用 Record

所有長期資訊以通用 Record 為基本單位。

不要求每筆資料必須歸入日記、研究或計畫等固定類別。

但可針對活動、待辦、來源及歷史狀態建立必要的結構化資料。

Record 至少需要表達：

- 穩定 ID。
- Schema Version。
- Revision。
- 建立時間。
- 文字正文。
- 作者或原始表述者。
- 提交管道。
- 內容性質。
- 必要的來源引用。
- 可選的事件時間。
- 原文核對狀態。
- 衍生來源及其版本。

未知資訊不得由 AI 任意補造。

---

# 5. Record 與 Revision

必須區分文字修正和現實世界的變化。

**Revision：** 修正同一紀錄的錯字、轉錄錯誤、原始日期錯誤或其他表示問題。

**新 Record：** 新事件、新決定、新想法或新的歷史狀態。

例如：

2026 年決定在日本工作。

2028 年決定回台灣發展。

這是兩個不同時期的決定，不能用新版本覆蓋舊決定。

AI 對歷史內容產生新的解讀時，也應建立衍生 Record，引用特定來源版本。

---

# 6. 來源、作者與內容性質

必須明確區分：

**作者：** 誰真正產生內容？

**提交管道：** 資訊透過哪個 Agent 或工具進入系統？

**內容性質：** 原文、摘錄、研究、摘要、推論或已確認的個人事項？

**證據來源：** 這項內容依據哪些紀錄、來源與版本？

使用者透過 Codex 保存日記，不代表 Codex 是作者。

使用者貼入 AI 研究報告，不代表 AI 報告是使用者原創。

AI 報告可能作為其他摘要的來源，但不因此變成外部一手證據。

重要引用必須追溯到 Record ID 與 Revision。

---

# 7. 原文保真

使用者原話必須和 AI 整理結果分開。

例如：

原話：「我可能明年想自己做產品，但還沒決定。」

AI 整理：「使用者曾考慮獨立產品開發。」

兩者不能互相取代。

透過 Agent 傳入的文字可能已經被轉述，因此必須區分：

- 已核對的原始文字。
- 使用者確認的整理文字。
- 尚未核對的 Agent 轉述。

系統不能單憑 Agent 的宣稱，就將文字標記為逐字原文。

---

# 8. 三種確認語意

系統需要區分：

**保存確認：** 同意將內容存入記憶庫。

**原文核對：** 確認文字與自己的原始表述一致。

**事實確認：** 明確確認某項個人決定、事件或內容狀態。

三者不能互相推導。

使用者同意保存 AI 的心理或職涯推論，不代表使用者承認推論正確。

介面應降低確認次數，不要求每次進行三次獨立操作。

---

# 9. 原始資料與衍生資料隔離

原始記錄、外部來源與 AI 衍生資料必須能清楚區分。

衍生資料包括：

- 摘要。
- 研究整合。
- AI 推論。
- 歷史分析。
- 知識關係。
- 必要的月度或年度摘要。

衍生資料必須保存來源參照。

不得將 AI 反覆引用自己的推論，視為證據增加。

對人格、心理狀態等敏感推論，預設不自動長期保存。

---

# 10. 寫入契約

預期流程：

使用者要求保存 → Agent 建立提案 → 使用者確認 → 核心檢查 → 正式保存 → 索引更新 → 回傳結果。

必須支援：

- 提案 ID。
- 與提案內容綁定的確認。
- 目標版本檢查。
- 操作 ID。
- 冪等提交。
- 提交結果查詢。
- 中斷恢復。

必要規則：

- 提案確認後內容改變，原確認失效。
- 同一操作 ID 和相同內容重試，不重複保存。
- 同一操作 ID 對應不同內容，拒絕。
- 目標 Revision 已變更，拒絕過期覆寫。
- 保存成功但索引失敗，必須保留已保存狀態並允許索引重建。

正式提交與搜尋索引完成是不同狀態。

重要提交資訊不能只存在於可重建的搜尋快取中。

---

# 11. 修改、撤回與刪除

修改既有紀錄時，需保留適當的版本歷史。

現實世界的想法改變，應建立新的歷史紀錄。

撤回舊決定不等於刪除當時曾經作出決定的事實。

隱私刪除則需要處理：

- 原始 Record。
- 相關 Revision。
- 衍生摘要。
- 搜尋索引。
- 版本歷史。
- 備份。
- 其他可控制的資料副本。

若來源因隱私刪除而失效，依賴該來源的衍生內容應先暫停一般查詢使用，再檢查是否需要重新產生、編修或刪除。

來源更新不代表舊摘要必然錯誤；歷史問題仍可能需要舊版本。

從舊備份還原時，必須避免已撤回或已刪除的資料未經處理就重新生效。

不能保證本機刪除會自動清除第三方 AI 平台已保存的資料。

---

# 12. Markdown 使用規則

主要資料格式候選為 Markdown + 結構化 Metadata。

資料應能讓人直接閱讀、備份及遷移。

但可讀不代表允許任何程式隨意改寫正式檔案。

MVP 建議：

- 正式寫入由 Memory Core 管理。
- 使用者可以直接閱讀與匯出。
- 未受控的外部修改必須被偵測。
- 未來如需直接編輯 Markdown，應建立正式匯入、版本驗證及衝突處理機制。

---

# 13. 研究與知識可靠性

可以保存完整的 AI 研究報告及其外部資料引用。

但研究報告本身不等於經過驗證的事實。

不要求所有內容都經過完整 Claims、Evidence、Knowledge、Review History 管理。

只對重要、反覆使用、容易過時或存在重大爭議的主張，按需建立進階驗證資料。

驗證時需區分：

- 來源是否存在。
- 來源是否支持主張。
- 是否有反面證據。
- 是否有多個獨立來源。
- 主張的適用時間和條件。
- 是否只是 AI 推測。

---

# 14. 搜尋需求

主要語言為繁體中文、日文及英文。

搜尋方案尚未定案。

候選技術：

- ripgrep。
- SQLite FTS5 加適當的 CJK 處理。
- Tantivy 加相容的 CJK 分詞。
- 按需導入的 Embedding。

必須測試：

- 中文短詞。
- 日文詞彙。
- 繁簡字形差異。
- 日本新字體與繁體漢字差異。
- 跨語言別名。
- 人名與專有名詞。
- 中日英混合查詢。

不應直接依賴預設 FTS5 分詞而假設中日文檢索品質已足夠。

---

# 15. 兩類查詢

**定位型查詢：**

尋找特定研究、日記或歷史事件。

可使用關鍵字、日期、來源及必要的語義搜尋。

**聚合型查詢：**

分析多年想法變化、反覆出現的構想或歷史模式。

不能只依賴 Top-k 搜尋。

可能需要：

- 範圍掃描。
- 分批分析。
- 階層摘要。
- 來源核對。
- 反例檢查。
- 搜尋覆蓋報告。

回答應說明實際檢索範圍，不得把部分資料分析描述成全量分析。

---

# 16. 長期分析限制

個人記憶庫不等於使用者完整生活紀錄。

因為一般對話不自動保存，系統可能存在資料選擇偏差。

例如只有遇到困難時才寫日記，就不能根據日記的負面內容比例推論整體生活狀態。

需要區分：

- 已保存紀錄中的趨勢。
- 使用者完整生活的真實趨勢。

沒有紀錄不等於沒有發生。

沒有完成紀錄，不等於事情確定沒有完成。

長期分析需留意時間缺口、紀錄密度及反面證據。

---

# 17. 活動與待辦

通用 Record 保存活動及計畫歷史。

但目前有效的活動狀態可能需要結構化資訊。

例如：

原訂 11 月 6 日開會，後來延後至 11 月 9 日。

歷史應保留兩項資訊，目前有效狀態則應指向新日期。

未來可建立 State Projection，包含：

- 活動識別碼。
- 時間與時區。
- 確認、暫定、取消等狀態。
- 修改時間。
- 來源及版本。

MVP 不承諾完整取代行事曆或任務管理工具。

---

# 18. AI 資料來源識別

需要區分：

- 模型自身知識。
- 當前對話。
- 平台提供的歷史背景。
- 本專案正式保存的記憶庫。
- 外部搜尋來源。

當使用者詢問資料庫是否保存某項內容，必須實際搜尋資料庫。

不能以 ChatGPT 歷史背景代替正式記憶庫。

搜尋結果需提供 Record ID、Revision、來源與必要引用片段。

查無紀錄時應說明搜尋限制，不得編造歷史。

---

# 19. 技術架構與可替換性

目前推薦：

AI Agent → CLI / MCP Adapter → Memory Core → 權威資料及可重建索引。

推薦技術方向：

- Python 核心。
- Markdown + Metadata。
- CLI 核心操作。
- 薄 MCP Adapter。
- SQLite 作為候選索引工具。
- 搜尋引擎依實測選擇。
- Git 作為輔助版本工具。
- 獨立加密備份。

上述為候選方案，不是不可推翻的要求。

不預先建立企業級資料庫、完整知識圖譜、大型 Agent Framework 或常駐雲端服務。

未來應能替換 AI 模型、Agent、搜尋引擎、Embedding 與索引實作。

---

# 20. 權限與安全

需要區分：

**操作防錯：** 防止重複寫入、過期版本、錯誤提交及部分失敗。

**權限隔離：** 防止 Agent 直接繞過核心程式修改正式資料。

**Prompt Injection 防護：** 防止外部內容被誤當成有效命令。

**資料外洩風險：** 避免私人資訊被不必要地讀取或傳送。

若 Agent 具有完整 Shell 和檔案權限，MCP 的確認流程不構成真正的安全隔離。

Windows 上的實際權限模型必須在投入長期私人資料前明確定義。

本機保存不代表使用雲端模型時完全離線。

---

# 21. 備份與恢復

系統必須能：

- 備份權威資料。
- 檢查備份完整性。
- 在另一個乾淨環境還原。
- 驗證 Record 與 Revision。
- 恢復來源引用。
- 重建索引。
- 保留必要的撤回及刪除狀態。
- 驗證資料遷移。

Git 不應是唯一備份。

對私人資料，應考慮加密備份。

---

# 22. 模型升級與重新解讀

未來模型可以重新閱讀及分析舊記錄。

不應每次模型升級就重新處理全庫。

優先重新分析：

- 當前問題涉及的資料。
- 存在錯誤或矛盾的研究。
- 有新證據的知識。
- 舊模型解讀不足的內容。
- 使用者指定的歷史主題。

新解讀必須引用原始來源版本，不能任意改寫當時的記錄。

---

# 23. MVP

第一版的核心驗證流程：

使用者提供文字 → Agent 準備提案 → 使用者確認 → 核心保存 → 新會話重新搜尋 → AI 引用正確來源與版本回答。

MVP 必須涵蓋：

- Record 與 Revision。
- 原文及衍生內容分離。
- 基本來源追蹤。
- 新增、修改、撤回及刪除。
- 冪等提交。
- 基本全文搜尋。
- 中日英搜尋測試。
- CLI 獨立操作。
- 至少一種 Agent 整合。
- 備份還原。
- 故障恢復。
- 明確安全能力與限制。

初期不強制實作：

- 全量 Claims 系統。
- 完整 Knowledge Graph。
- 大型向量資料庫。
- 自動月度整理。
- 自動重新分析整個歷史。
- 完整行事曆。
- 多 Agent 自主協作。
- 大型 GUI。

---

# 24. 驗收與實驗

使用兩種資料集：

**真實代表性語料：** 約 100–300 份文件、約 50 題問題，測試查詢品質、來源與時間語意。

**規模壓力語料：** 約 5,000–12,000 份模擬資料，測試效能、資源、索引與恢復能力。

必須測試：

- 原文是否一致。
- Record 與 Revision 是否正確。
- 重試是否冪等。
- 提案修改後確認是否失效。
- 索引故障時是否保留主資料。
- 刪除後衍生內容是否仍不當透露資訊。
- 舊備份是否讓已刪除資訊重新生效。
- CJK 搜尋召回。
- 聚合查詢覆蓋與反例。
- Agent 的誤查及漏查。
- 來源引用與推論污染。
- Token 成本。
- 日常保存操作的負擔。

測試完成前不預先宣稱特定準確率。

# 25. 開發策略

先進行技術評估與現成專案比較，再建立受控的端到端原型。

優先證明：

1. 文字可以忠實保存。
2. 資料可以可靠取回。
3. Agent 能引用正確來源與版本。
4. 修改、撤回與刪除有明確行為。
5. 故障與重啟後能恢復使用。

再按實際需求增加：

- 進階搜尋。
- 跨時間聚合。
- 語義搜尋。
- 知識驗證。
- 重要知識關係。
- 未來模型重新解讀。

# 26. 最終產品原則

本專案不是單純的 AI 聊天紀錄備份工具，也不是一般筆記編輯器。

它是一套由個人持有、可透過不同 AI Agent 使用的長期記憶基礎設施。

最重要的原則是：

**AI 可以重新理解記憶，但不能任意改寫歷史。**

**使用者同意保存 AI 分析，不等於承認分析正確。**

**沒有找到紀錄，不代表事情沒有發生。**

**來源刪除時，衍生資料也必須納入處理。**

**資料保存要可靠，系統複雜度則必須有實際需求支持。**

**最終目標是讓個人知識與歷史能持續使用五年、十年甚至更長時間，而不受特定 AI 工具限制。**
